# Trading Bot

Python research/backtesting project for Indian equities (Nifty 50 and Nifty
500 universes), built on `yfinance` + DuckDB. See `ARCHITECTURE.md` for the
full module map and `research/README.md` for the signal-screening layer and
its CLI (`research/screen.py`).

This file documents `backtest_cli.py` — the CLI for `backtest.py` +
`strategies/` — plus a quick pointer to the data-pipeline scripts that
populate the universe these commands run against.

---

## Data pipeline scripts

These aren't CLIs (no flags — edit the constants at the top of each file to
change scope) but they're the scripts that get data into the DB in the
first place. Full function-level detail is in `ARCHITECTURE.md`'s module
reference; this is just "what do I run, and why."

- **`main.py`** — one-shot: ingest 1 year of daily OHLCV for the active
  (Nifty 50) universe. The simplest starting point.
- **`extend_history.py`** — re-fetch up to N years (default 5) of history
  for the active universe and rebuild indicators + signals on top of it.
- **`extend_universe_nifty500.py`** — expand the tracked universe from
  Nifty 50 to Nifty 500 and extend history to ~12 years. This is a large,
  long-running job (hundreds of symbols), so it's built around
  `src.universe.resumable_bulk_fetch`: safe to interrupt (Ctrl-C, crash,
  timeout) and re-run — already-fetched symbols are skipped rather than
  re-downloaded, and every attempt is logged to a `fetch_checkpoint` table
  so you can see exactly what succeeded, failed, or was skipped across
  multiple runs. **Known limitation, printed as a warning every time this
  runs:** Nifty 500 membership reflects *current* constituents only —
  projecting that back 12 years introduces survivorship bias (companies
  delisted/removed/renamed out of the index over that window aren't
  included). This is a deliberate, accepted tradeoff, not an oversight —
  keep it in mind when interpreting backtest results built on this dataset.

## CLI Manual: `python -m backtest_cli`

Interactive CLI for `backtest.py` + `strategies/`: list what's registered,
see each strategy's tunable parameters, run a backtest (with parameter
overrides) against a single symbol or the full active universe, and revisit
or compare stored results — without writing a one-off script each time.
Mirrors `research/screen.py`'s style (same `argparse` subcommand shape,
same load → compute → print → save flow).

Important distinction from `screen.py`: this CLI's `run` command *does*
write to `signals` and `backtest_runs`/`backtest_trades`/`backtest_results`
— unlike screening, a backtest run is meant to be a durable, queryable
record.

Run from the project root. `--help` is available at every level and always
up to date (it's generated by `argparse` from the same flags described
below, not maintained separately):

```
python -m backtest_cli --help
python -m backtest_cli list-strategies --help
python -m backtest_cli list-params --help
python -m backtest_cli run --help
python -m backtest_cli show-results --help
python -m backtest_cli compare --help
```

### Command: `list-strategies` — what's registered

```
python -m backtest_cli list-strategies
```

No flags. Prints each registered strategy's name, one-line description
(the first line of its class docstring), and required input columns.

### Command: `list-params` — a strategy's tunable parameters

```
python -m backtest_cli list-params --strategy NAME
```

| flag | required | default | meaning |
|---|---|---|---|
| `--strategy` | yes | — | registry name, e.g. `sma_crossover` |

Prints each parameter's name, default value, and description (pulled from
`StrategyConfig.param_info()` — see `ARCHITECTURE.md` for how that's wired
up). Unknown strategy name → clear error listing what's available and
suggesting this command.

**Example:**

```bash
python -m backtest_cli list-params --strategy bollinger_breakout
```

### Command: `run` — run a backtest

```
python -m backtest_cli run --strategy NAME [--params "k=v,k2=v2"]
    [--symbol SYMBOL] [--start YYYY-MM-DD] [--end YYYY-MM-DD]
    [--initial-capital N] [--position-sizing equal_weight]
    [--slippage-pct N] [--max-positions N] [--output-dir DIR]
```

| flag | required | default | meaning |
|---|---|---|---|
| `--strategy` | yes | — | registry name, e.g. `sma_crossover` |
| `--params` | no | strategy's own defaults | `"key=value,key2=value2"` — unknown keys or values that fail the strategy's `validate()` (e.g. `fast_window >= slow_window`) error clearly rather than running anyway |
| `--symbol` | no | full active universe | a single symbol (e.g. `RELIANCE`); unknown symbol → error listing example valid ones |
| `--start` / `--end` | no | full available data range | backtest window (`YYYY-MM-DD`) |
| `--initial-capital` | no | `1000000` | starting capital |
| `--position-sizing` | no | `equal_weight` | only value currently implemented |
| `--slippage-pct` | no | `0.05` | slippage in percentage points |
| `--max-positions` | no | `10` | max concurrent open positions |
| `--output-dir` | no | `results/backtests` | where the results JSON lands |

**Examples:**

```bash
# Default SMA crossover (20/50), full active universe, full available history
python -m backtest_cli run --strategy sma_crossover

# Custom windows, single symbol, explicit date range
python -m backtest_cli run --strategy sma_crossover --params fast_window=10,slow_window=30 \
    --symbol RELIANCE --start 2023-01-01 --end 2024-12-31

# Bollinger breakout with a tighter band, custom slippage/position cap
python -m backtest_cli run --strategy bollinger_breakout --params "window=15,num_std=1.5" \
    --symbol TCS --slippage-pct 0.1 --max-positions 5
```

What it does, in order: looks up the strategy, applies `--params` on top of
defaults and validates the result (`Strategy.__init__` calls
`config.validate()` automatically), resolves the symbol scope and date
range, generates signals (`src.strategy.run_strategy` — a separate step
from backtesting, not something `run_backtest()` does itself) and stores
them in `signals`, runs the backtest (`backtest.run_backtest`) and stores
the result in `backtest_runs`/`backtest_trades`/`backtest_results`, prints a
console summary (params used, date range, symbol scope, metrics, top/bottom
5 trades by net PnL), and saves the same summary as
`{strategy}_{run_id[:8]}_{timestamp}.json` in `--output-dir`.

**Signal-name collision note:** `rsi_mean_reversion` and
`bollinger_breakout` store signals under one fixed name regardless of
`--params` (unlike `sma_crossover`, which folds its windows into the stored
name, e.g. `sma_crossover_10_30`). Running either of those two again later
with *different* `--params` overwrites previously stored signals at
overlapping symbol/date rows — the CLI prints an explicit `Note:` about
this every time you run one of them.

### Command: `show-results` — revisit a stored run without re-running it

```
python -m backtest_cli show-results --run-id RUN_ID
python -m backtest_cli show-results --latest --strategy STORED_NAME
```

| flag | required | meaning |
|---|---|---|
| `--run-id` | one of these two | exact `run_id` to show |
| `--latest` | one of these two | show the most recent stored run for `--strategy` |
| `--strategy` | only with `--latest` | the exact **stored** `strategy_name` (e.g. `sma_crossover_20_50`) — not necessarily the registry key, since `rsi_mean_reversion`/`bollinger_breakout` always store under their flat base name regardless of params |

**Examples:**

```bash
python -m backtest_cli show-results --run-id 6081853a-63da-4e43-a4ec-eb02e103a96e
python -m backtest_cli show-results --latest --strategy sma_crossover_10_30
```

**Known limitation:** `backtest_runs` doesn't persist the symbol scope or
individual `--params` values a run used — only the stored `strategy_name`
string. So `show-results` prints `Params: not recoverable from stored data`
unless you still have the JSON that `run` saved at the time (that file
always has the full params). Symbol scope *is* reconstructed here, from the
distinct symbols in `backtest_trades` — except for a run that closed zero
trades, where there's nothing to reconstruct it from either.

### Command: `compare` — side-by-side metrics across runs

```
python -m backtest_cli compare --strategy NAME1,NAME2,...
python -m backtest_cli compare --run-ids ID1,ID2,...
```

| flag | required | meaning |
|---|---|---|
| `--strategy` | one of these two | comma-separated **stored** `strategy_name`(s); compares each one's most recent run |
| `--run-ids` | one of these two | comma-separated exact `run_id`(s) to compare directly |

**Examples:**

```bash
python -m backtest_cli compare --strategy sma_crossover_20_50,rsi_mean_reversion,bollinger_breakout
python -m backtest_cli compare --run-ids 6081853a-63da-4e43-a4ec-eb02e103a96e,a31452b9-a25f-4cbe-9eab-797fc4ba7908
```

Prints one row per run — `strategy_name`, `run_id` (first 8 chars), `cagr`,
`sharpe_ratio`, `max_drawdown_pct`, `win_rate`, `total_trades` — **sorted by
Sharpe ratio descending**, mirroring the comparison-table style already
used for the three-strategy comparisons run earlier in this project. A
name/run_id with no stored runs is skipped with a warning, not a hard
failure, so one typo doesn't kill the whole comparison.

### Tips

- `list-params` before `run` if you're not sure what a strategy's fields
  are called — `run` rejects unknown parameter names outright rather than
  silently ignoring them.
- Every registered strategy auto-validates its config at construction time
  (`fast_window < slow_window` for SMA, `0 ≤ oversold < exit ≤ 100` for RSI,
  a supported `exit_mode` for Bollinger) — an invalid `--params` combination
  fails immediately with a clear message, before touching the database.
- `--symbol` takes exactly one ticker, with or without `.NS`; there's no
  comma-separated custom-watchlist option here (unlike `screen.py`'s
  `--universe`) — omit it to run the full active universe instead.
- Results are always persisted to `backtest_runs`/`backtest_trades`/
  `backtest_results` regardless of `--output-dir` — the JSON file is a
  convenience for diffing runs without querying the DB, not the primary
  record.
